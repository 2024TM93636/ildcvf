## 1. Deviation Summary

During the sixth measured attempt of the E6 LLM Reliability campaign, the operator reused the operator-supplied authorization value previously used for the fifth measured attempt. The reused authorization value was also exposed in PowerShell terminal output.

Subsequent investigation established that the PowerShell launcher forwarded the same operator-supplied value through both (1) the `ILDCVF_E6_MEASURED_AUTHORIZATION` environment variable and (2) Maven execution arguments carrying the expected controller authorization. The Java authorization gate compared these two values. Because both originated from the same operator-supplied input, this comparison did not independently authenticate a Review Controller decision.

The inspected authorization mechanism did not bind authorization to the scheduled attempt identifier or enforce single-use authorization. The sixth attempt executed and produced a permanent scientific observation.

**Deviation classification:** Authorization-control and procedural-integrity failure.  
**Scientific disposition:** Observation #6 is scientifically admissible under the Review Controller's accepted M10 Step 14G decision, subject to documented verification qualifications.  
**Deviation disposition:** E6-PD-001 remains OPEN.

Scientific admissibility must not be interpreted as procedural compliance or completed security remediation.

## 4. Expected Authorization Procedure

The intended controlled execution procedure required: (1) a scheduled, previously unrecorded measured attempt; (2) explicit Review Controller authorization for that specific attempt; (3) authorization verification before any provider invocation; (4) exactly one provider invocation; (5) no retry; (6) permanent preservation of the observation; and (7) fresh Review Controller permission before subsequent attempts.

For the sixth attempt, authorization specifically issued for `llm-002-request-add-field-r2` was expected. An operator-supplied value previously used for `llm-002-request-add-field-r1` should not have authorized the sixth attempt.

**Important distinction:** These were intended procedural requirements; the inspected implementation did not enforce all of them.

## 5. Actual Observed Behavior

1. The operator reused the fifth attempt's operator-supplied authorization value for the sixth attempt.
2. That value was exposed in PowerShell terminal output.
3. PowerShell assigned it to `ILDCVF_E6_MEASURED_AUTHORIZATION`.
4. PowerShell also forwarded it as the expected authorization argument through Maven.
5. Java compared the environment authorization against the expected authorization argument.
6. The comparison succeeded despite reuse, without independent controller authentication.
7. The sixth attempt executed and produced a permanent result.
8. The result recorded one provider invocation and zero retries.

No authorization value or credential is reproduced here.

## 6. Confirmed Root Cause

### 6.1 Primary technical root cause

Authorization verification was self-referential. PowerShell supplied the same operator-controlled value through two channels; Java tested whether they matched. Constant-time equality does not establish authorization authenticity, freshness, scope or independent origin. The gate verified equality of two representations of one supplied value rather than independently authenticating a Review Controller decision.

### 6.2 Missing authorization controls

The inspected gate did not establish independent controller-issued authorization verification, binding to the scheduled attempt ID, persistent single-use enforcement, or rejection of authorization previously consumed by a different attempt. These omissions permitted reuse on an unrecorded sixth attempt.

### 6.3 Operational contributing factor

The operator supplied the value previously used for the fifth attempt while executing the sixth. The value was additionally exposed in terminal output. Operator error and authorization-design defect are distinct; correctly enforced attempt-scoped authorization should reject authorization intended for another attempt.

### 6.4 Controls that existed separately

The implementation separately refused attempts with existing results, limited measured execution to one provider invocation, recorded zero retries and used create-new result export. Those controls did not prevent reuse of an authorization value on a different unrecorded attempt.

## 7. Security and Procedural Impact

### 7.1 Confirmed impact

**VERIFIED:** A previously used operator-supplied authorization value was accepted for a later attempt; it was exposed in PowerShell terminal output; the Java gate lacked independent controller authentication and attempt binding; and the sixth provider execution occurred despite the authorization-procedure deviation.

### 7.2 Potential exposure boundaries

The value was forwarded through Maven arguments, creating a potential process-command-line exposure boundary. Depending on host configuration, command-line arguments may be observable through process inspection, diagnostic capture or logging. No external observation through those channels was established. Terminal disclosure itself is confirmed.

### 7.3 Procedural impact

The sixth execution did not satisfy the intended fresh, attempt-specific authorization procedure. It must not be described as procedurally compliant. Documentation, remediation review and explicit controller disposition are required before campaign resumption.

## 12. Corrective and Preventive Action Recommendations

**Status: RECOMMENDED ONLY â€” NOT IMPLEMENTED.**

### 12.1 Immediate containment

Maintain suspension of further E6 measured provider executions; treat the exposed value as compromised and unsuitable for reuse; preserve all six observations and the investigation trail; avoid further credential disclosure; do not retry observation #6 or execute observation #7 without explicit authorization following remediation review. ### 12.2 Authorization architecture remediation

Subject to separate approval, implement independently verifiable controller authorization scoped to campaign, protocol and attempt ID; fresh authorization per attempt; persistent replay protection; verification before provider invocation; separation of operator input from the independent verification authority; removal of authorization values from process-command-line arguments; and fail-closed behavior for missing, mismatched, expired, reused or invalid authorization. ### 12.3 Offline security verification

Test missing and invalid authorization; attempt-ID mismatch; consumed-token reuse; replay across process restarts; duplicate attempts; existing-result refusal; exactly-once and zero-retry controls; missing verification material; and rejection before any provider transport invocation. Use offline tests only, without Groq requests.

### 12.4 Scientific-boundary regression verification

Test that changing authorization inputs cannot alter frozen model configuration, prompt/schema, grounded evidence, scenario fingerprints, request body, deterministic validation, ground-truth comparison, hallucination classification or scientific result fields (except separately approved administrative metadata, if introduced). Do not alter measured observations.

### 12.5 Credential and diagnostic safety

Prevent values from appearing in PowerShell echo, errors and debug traces; avoid Maven command-line secrets; redact diagnostic and exception paths; exclude authorization values from scientific artifacts; retain auditable authorization scope and consumption without exposing secrets; document safe operator handling; and test replacements without real credentials.
